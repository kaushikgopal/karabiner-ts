How karabiner-ts is built

TypeScript generates a Karabiner-Elements configuration. At runtime, Karabiner sends selected shortcut commands to a persistent Swift server that moves macOS windows.

This page describes the working-tree source at the time of writing. Generated output and the installed configuration can differ until generation and installation run.

From a key press to a window

  1. Author. createMainRules() in src/rules.ts builds mappings and version 3 user-command payloads. karabinerRule() in src/builders.ts turns mappings into manipulators.
  2. Generate. src/main.ts writes buildKarabinerJson(). src/config.ts assembles the selected profile, rules, devices, and parameters; src/serialize.ts and src/json.ts serialize and print it as karabiner.json.
  3. Install. The default make target generates the repo file and copies it to ~/.config/karabiner/karabiner.json. This does not rebuild or restart the server.
  4. Dispatch. Karabiner matches the key and sends the send_user_command payload to its user-command receiver socket. ServerMain.swift decodes it and submits it to CommandCoordinator.
  5. Execute. WindowManager resolves the target and uses macOS Accessibility (AX) APIs. For a cycle, CycleTracker selects a step and LayoutCalculator computes a frame. The move-display command takes a separate path.

Sources: Makefile, ServerMain.swift, CommandCoordinator.swift, WindowManager.swift.

The generator and server run at different times. karabiner.json carries the runtime policy; it does not contain or start the Swift server.

Repository map

TypeScript generator

  • src/rules.ts — shortcut definitions, layouts, payloads, and keyboard rules.
  • src/builders.ts — mapping DSL, conditions, and layer manipulators.
  • src/types.ts — configuration model and key-code names.
  • src/config.ts, src/serialize.ts, src/json.ts — profile assembly and JSON output.
  • src/rules.test.ts — tests for the generated rules and payloads; src/rules.sample.ts shows the DSL.

Swift runtime

  • kg-windowlayout-karabiner-server/Package.swift — macOS executable, receiver dependency, and test target.
  • LayoutCommand.swift — command decoding, models, defaults, and validation.
  • WindowManager.swift, LayoutCalculator.swift, DisplayGeometry.swift — AX operations and geometry.
  • CycleTracker.swift, FocusMonitor.swift, FocusSuppression.swift, WorkspaceActivationMonitor.swift — cycle and focus state.
  • Tests/CustomKarabinerWindowLayoutServerTests/ — command, geometry, cycle, and observer tests.

src/serialize.ts follows Kotlin field order and JSON names. JsonDouble in src/json.ts retains a decimal on integral doubles. The project started as a Kotlin port; do not assume byte parity with the sibling without checking it.

Other rules in src/rules.ts include Right Command → Right Control, Caps Lock as Escape/Hyper, Vim-style navigation, and J/F layers. Hyper uses the four right-side Control, Command, Option, and Shift modifiers. Layer mappings produce a variable-gated manipulator and a simultaneous-key manipulator.

Window shortcuts

Hyper means Caps Lock held as the four right-side modifiers. These shortcuts use the visible screen frame. All app launchers activate their target and use the existing screen of the focused window.

KeysCurrent behavior
Hyper+11Password: one bottom-right layout.
Hyper+M / W / O / SMessages, WhatsApp, Obsidian, Slack: alternate tall and wide layouts with app-specific offsets.
Hyper+0Spotify: one full-height left layout with an 800-point width constraint.
Hyper+BFirefox: alternate tall and wide layouts; apply to all usable windows with a 48-point cascade.
Hyper+TRex first; Ghostty is the fallback. Alternate centered tall and wide layouts without an offset.
Hyper+Up / DownFrontmost window: alternate the corresponding half and two-thirds.
Hyper+Left / RightFrontmost window: cycle through the corresponding half, one-third, and two-thirds.
Hyper+FFrontmost window: visible-frame fill, centered 90% × 90%, then the frame captured at the start of the cycle. Fill is not macOS fullscreen.
Hyper+DMove the frontmost usable window to the next display; preserve its size and relative offset where possible.

Source: src/rules.ts — appWindowShortcuts, directionalWindowShortcuts, fillWindowShortcuts, and createMainRules().

For app targets, a running background app is activated without resizing. The next press starts at layout 0. A newly launched app gets its first layout after its focused window is available.

The server checks the ordered primary and fallback bundle identifiers and selects the first that is running or installed. Thus installed Rex wins even if Ghostty is already running. If no candidate is available, the server logs an error and returns.

Sources: LayoutCommand.swift — ApplicationTarget.firstAvailableBundleIdentifier; WindowManager.swift — cycleApplication.

The user-command contract

cycle_window_layout

Version 3 payloads carry a cycle_id, application or frontmost target, screen strategy and frame, window scope, cascade offset, layout list, and policy groups.

  • Application targets may include ordered fallback_bundle_identifiers, plus open and activation flags.
  • Each layout contains four fraction-plus-points insets, resize anchors, optional minimum/maximum sizes, and optional restore_original.
  • Filters, post-layout focus, cycle resets, and timeouts are encoded in the payload.

move_window_to_display

Version 3 carries screen_frame, window_filter, focus_after_layout, and timeouts. It has no layout list or cycle ID.

The server moves the focused usable window to the next entry in NSScreen.screens, wrapping at the end. With one display, it does nothing.

Current rules reject non-standard, minimized, and fullscreen windows; the server also requires a positive-size AX window. The rules request raise and refocus. They set a 1-second AX timeout, 5-second application and focused-window waits, and 25-ms polling.

Both application and frontmost cycle payloads request reset-on-app and reset-on-focused-window behavior. App-cycle payloads additionally request focus-only activation and reset when the target is not frontmost. The move command has no cycle policy of its own; the coordinator uses its default cycle policy.

UserCommand.decode rejects unsupported versions and unknown commands. Cycle commands also require a nonempty cycle ID and layouts, valid size constraints, and valid timeouts. Optional policies receive Swift defaults; the cycle decoder also supports the legacy target reset field. The move decoder applies defaults but does not perform the cycle decoder's timeout-value validation.

Sources: src/rules.ts — policyGroups and command builders; LayoutCommand.swift — UserCommand.decode and policy models.

Inside the Swift server

  1. Receive and coordinate. ServerMain retains a KEUserCommandReceiver on the default socket. Invalid payloads are logged. CommandCoordinator.submit cancels prior tasks before starting a new one.
  2. Select a cycle step. CycleTracker stores one current command/window/index state, not an independent history for every window. A matching command and window advance modulo the layout count; another command/window or a reset starts at index 0. Activation and focused-window notifications can clear the state. Focus suppression prevents the server's own raise/refocus notification from immediately resetting it.
  3. Compute a frame. DisplayGeometry converts AppKit screen coordinates to AX coordinates. LayoutCalculator.frame resolves each inset as screen dimension × fraction + points, applies size limits and anchors, and computes a frame. Cascading offsets are clamped to the reference frame.
  4. Apply or restore. WindowManager.apply captures each selected window's frame at cycle index 0. A restore step uses that saved frame. Other steps set position and size, then re-anchor using the size the app actually accepted. The configured raise/refocus operations follow.
  5. Move displays separately. moveFrontmostWindowToNextDisplay chooses the source by window center, or largest screen overlap, then translates the window by the reference-frame origin difference. It clamps the origin to the destination; an oversized window is pinned to the leading edge. No cycle index is advanced.

Sources: ServerMain.swift, CommandCoordinator.swift, CycleTracker.swift, DisplayGeometry.swift, LayoutCalculator.swift, WindowManager.swift.

Build, install, and checks

TargetEffect
make / make tsGenerate karabiner.json and copy it to the Karabiner config directory.
make generateGenerate the repo file without installing it.
make test / make checkRun Bun tests / TypeScript type checking.
make install-window-serverBuild a release app, remove the previous installation, reset its Accessibility grant, sign and install the app and LaunchAgent, briefly start it for the prompt, then stop it and open Settings.
make restart-window-serverBootstrap the installed LaunchAgent after granting Accessibility permission.
make restart-karabinerRestart Karabiner's console user server.

WARNING: Installing the window server removes the previous app and resets its Accessibility grant. Enable the server in System Settings before restarting it. Ordinary rule changes need configuration generation and installation, not a server rebuild.

README.md describes a make parity target, but the current Makefile does not define one. Treat parity as an unverified historical goal, not a current check.

Sources: Makefile, README.md, LaunchAgent template.
